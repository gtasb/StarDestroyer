# 判定与复核规则

## 三个状态

| 状态 | 触发条件 | 报告里怎么写 | 下一步 |
|---|---|---|---|
| `confirmed` | 语句级污点 trace 完整（源与汇都被定位） | 直接报，附调用链 | 无需复核 |
| `needs_review` | 有路径，或 trace 断在中间 | 报，但标注「参数可控性/断点未证」 | 人工看 `missing` 字段 |
| `needs_dynamic` | 链跨第三方库或反射，静态不可达 | 报，进动态验证队列 | 运行时复现 |
| `no_finding` | 两引擎均无命中 | 不报 | — |

## 复核时的检查顺序

1. **入口是否真的外部可达**。`@RequestParam` 不等于公网可达；先看路由与鉴权。
2. **污点是否被隐式净化**。类型转换、白名单、`Integer.parseInt`、ORM 绑定都会断链。
3. **sink 是否真的执行**。`Statement` 是否真被调用，还是死代码 / 被 try 吞掉。
4. **权限影响**。同一漏洞在只读接口与管理接口上优先级差一个数量级。

## 不允许做的事

- 不允许因为「看起来像漏洞」把 `needs_review` 直接改写为 `confirmed`。
- 不允许在没有源码证据时补写调用链节点（反射、代理、SPI 断边尤其）。
- 不允许把 LLM 的叙述当作判定依据；LLM 只写说明，状态来自 `core/verdict.py`。

## 误报的常见来源

- 框架层已转义（Thymeleaf、Spring 的 `@PathVariable` 类型转换）。
- 参数来自配置而非请求（`@Value`、`Environment`）。
- 测试代码、示例代码、注释掉的代码。
